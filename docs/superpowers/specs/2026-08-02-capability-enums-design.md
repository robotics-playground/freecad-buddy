# Report the live property enumerations — DW-92

## Problem

`feature_pattern`'s `mode` cannot be given a value that works on both blocking CI legs. Verified:
FreeCAD 1.0.0 declares `{"length", "offset"}` for a linear pattern and `{"angle", "offset"}` for a
polar one; FreeCAD 1.1.1 reports `['Extent', 'Spacing']` for both. `TransformMode` diverges the
same way — `{"Transform tool shapes", ...}` against `['Features', 'Whole shape']`.

The tools already handle this correctly: `_checked_enum` validates against
`getEnumerationsOfProperty` at call time, and a tool leaves the property unset when the caller
omits it, so both legs work. The gap is **discoverability**. The wire schema types these fields as
a bare `{"type": "string"}` with no enum, so a client cannot learn the legal set without making a
call and reading the rejection. An agent that learns `mode: "Extent"` on 1.1.x gets
`INVALID_INPUT` on the 1.0.x leg with no way to have known better.

DW-92 names `mode`, but the same gap covers every property `_checked_enum` guards.

## Scope

**In:** `query_capabilities` gains an `enums` block reporting the live enumeration for each
`(type_id, property)` pair the feature tools validate.

The six properties, read from the `_checked_enum` call sites in `features.py`:

| type_id | property | measured on 1.1.1 |
| --- | --- | --- |
| `PartDesign::Pad` | `Type` | `Length, UpToLast, UpToFirst, UpToFace, ?TwoLengths, UpToShape` |
| `PartDesign::Pocket` | `Type` | `Length, ThroughAll, UpToFirst, UpToFace, ?TwoLengths, UpToShape` |
| `PartDesign::Revolution` | `Type` | `Angle, UpToLast, UpToFirst, UpToFace, TwoAngles` |
| `PartDesign::Hole` | `ThreadType` | 11 values, `None` first |
| `PartDesign::Hole` | `HoleCutType` | `None, Counterbore, Countersink, Counterdrill` |
| `PartDesign::Hole` | `DepthType` | `Dimension, ThroughAll` |
| `PartDesign::Chamfer` | `ChamferType` | `Equal distance, Two distances, Distance and Angle` |
| `PartDesign::LinearPattern` | `Mode`, `TransformMode` | `Extent, Spacing` / `Features, Whole shape` |
| `PartDesign::PolarPattern` | `Mode` | `Extent, Spacing` |

**Out:** `feature_set_parameters`' `_checked_enum` call. It validates whatever property the caller
names, so its set is open and cannot be enumerated ahead of time.

**Out:** putting enums in each tool's JSON schema. A JSON Schema `enum` is static, and these
values are build-dependent — baking one in would state as fixed exactly the thing that varies.
That is the defect, not the fix.

## Behaviour

```
query_capabilities() -> { ..., "enums": { "<type_id>": { "<property>": [ ... ] } } }
```

Values are reported **verbatim**, in FreeCAD's own order, with no filtering.

**The `?` prefix is deliberate and must not be stripped.** `Pad.Type` reports `?TwoLengths`, and
measurement shows it is a legal value: assigning it succeeds and it reads back unchanged. It is
not a disabled member to be cleaned away — filtering it would hide a value callers can use, and
`_checked_enum` already accepts it.

A property that cannot be probed on the running build is **omitted** rather than reported empty,
so a consumer can tell "this build has no such enumeration" from "this build offers no values".

## Structure

The probe belongs in `shim.py` beside the other capability probes, cached per process like them:
one throwaway hidden document, one object per distinct `type_id`, `getEnumerationsOfProperty` per
property. `shim.capability_banner` gains the block, so `query_capabilities` needs no new logic.

`CapabilityBanner` gains `enums: dict[str, dict[str, list[str]]]`. The generated JSON Schema is
regenerated by `scripts/gen_schemas.py` and the drift check keeps them in step.

## Cost

Ten `getEnumerationsOfProperty` reads on a throwaway document, once per process, folded into the
existing capability warm-up. It is the same shape of work `varset_backend` already does.

## Testing

In-FreeCAD:

1. Every listed `(type_id, property)` pair appears in the block with a non-empty list.
2. `PartDesign::LinearPattern.Mode` matches what `getEnumerationsOfProperty` returns live — the
   DW-92 case, asserted against the live probe rather than a hardcoded expectation, since
   hardcoding `['Extent', 'Spacing']` would fail the 1.0.x leg and reintroduce the very
   version-coupling this fixes.
3. A `?`-prefixed value survives into the block unfiltered.
4. A pair the build cannot probe is absent, not empty.

External: `CapabilityBanner` carries `enums` and `gen_schemas --check` reports no drift.

The generated schema types `enums` as a bare `{"type": "object"}`, not as an object of objects of
string arrays. That is a pre-existing limitation of the generator — `_schema_for` maps every
`dict[...]` annotation to `{"type": "object"}` with no key or value typing, and several existing
contract fields are already emitted that way. Narrowing it would mean teaching the generator to
emit `additionalProperties` for parameterised dicts, which is its own change and is not in scope
here. The wire value is still validated by the required-field check; only its interior shape is
unconstrained.

## What this does not do

It does not make one literal `mode` string work on both legs — nothing can, because the two
FreeCAD versions genuinely disagree. It lets a client discover the legal set for the build it is
talking to, which is the most that is true.

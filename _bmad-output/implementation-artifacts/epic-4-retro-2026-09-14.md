## What went right

**The entry gate did its job.** Story 4.1 authored the measures before any designer code existed,
and those measures then caught real defects in the code written against them — including two dev
specs that cannot decide a wrong part (DW-122). That is the AD-19 discipline paying off rather than
being ceremony.

**Validators refused to certify themselves.** Every unmeasurable validator recorded a `not_scored`
reason naming what was missing, rather than a fabricated `0.0` or `1.0`. `faults G3` currently
reports two UNMEASURED validators and the gate correctly refuses a verdict. The G2 history
(DW-93/DW-98: scores published over populations that were not the suite) is the failure this
avoided.

**Looking at output found what assertions could not.** The judge sheet passed every automated check
in its story while printing a thickness callout under the one view that cannot show thickness
(DW-121). Only rendering the PNG and reading it caught that. The same lesson repeated in the spike:
the decision note's central claim was confirmed only because a test asserted it executably, and the
first version of that test was itself wrong (it read `sys.modules` instead of spawning a fresh
process, DW-125).

**The spike changed the epic's shape before code was written.** Page export is GUI-only, so 4.3
composes a sheet instead of exporting one. Discovering that in 4.1 rather than mid-4.3 is the whole
reason the entry gate front-loads spikes.

## What went wrong

**Duplicate ledger numbers.** Several agents and I allocated DW-116/117/121/122/123/124
concurrently, producing six collisions and one entry duplicated in content. Fixed by renumbering and
deleting the redundant one, but the ledger has no allocation protocol and concurrent writers will
collide again. **Action: give `deferred-work.md` a reserved-range or timestamp-based id scheme before
the next multi-agent run.**

**Phantom flaky test.** I chased an intermittent `test_g3_gate.py` failure across five full suite
runs before establishing it was my own doing — reading `benchmarks/g3/` files while an agent was
writing them. **Action: do not run the full suite while an implementation agent is mid-edit; the
result is not measuring the tree you think it is.**

**Two stories needed rework after review.** 4.1's TechDraw probe passed alone and failed in the full
suite; 4.3's sheet passed its tests and was visually wrong. Both were caught, but both were reported
`done` by their implementer first. **Action: the visual/behavioural check belongs inside the story's
own verification, not only in review.**

## What was not done and why

**Story 4.7's exit run did not happen, and that is the correct outcome.** Its own Block If forbids
unsealing while any cited validator is `not_scored`. Two are:

- `verify_recompute` — cited by G3.2/G3.3, no fault suite exists. Being authored now; this is
  ordinary work with no external blocker.
- `visual_judge` — needs a vision-model credential that does not exist on this machine
  (decision 017), plus fixtures that a judge can be shown.

Unsealing against an incomplete implementation would burn the held-out set permanently, and its
replacement would be strictly weaker because the author would by then have seen the dev set's
failures. The set remains sealed with `unseal_events: []`.

**The seal is machine-keyed, not operator-held** (DW-116). The frozen intent asked for an
operator-held key; the operator was asleep. The DW-99 protection that matters is intact — no
plaintext ever reached git — but the set is not protected against whoever holds the key. Re-sealing
under a human-held key is cheap while `unseal_events` is still empty, and should happen before any
exit run.

**UAT TC-16-03 was not run.** Driving FreeCAD's Python console through the accessibility tree did not
resolve within a reasonable attempt budget. TC-16-01, -02 and -04 all PASS, so the capability
boundary is confirmed on both legs; what is unverified is whether the GUI and headless projections
agree geometrically.

## Honest limits on what the numbers mean

- `corrupted_plan` 1.000 / 0.000 is measured over **8 of 10** planted cases; two are excluded with
  their measurements attached (DW-122).
- Every loop run in scoring terminated `CAP_EXHAUSTED`, because with no model backend the planner
  cannot actually repair. Detection came from the final measurement, not from a converging loop. The
  loop's *control flow* is proven deterministically; its *convergence rate* is not.
- No vision model has read a composed sheet. The visual leg is built and fail-closed, not validated.
- The Spreadsheet parameter fallback is implemented but unexercised — VarSet is available on both
  legs here, so nothing on this machine tests it.

## Addendum — the operator's correction, and what it unblocked

After the retrospective above was written, the operator corrected a conflation that had propagated
through several stories and into this document: **grading the visual-judge fault suite never needed
a credential.** A vision-capable agent reads the rendered PNGs directly.

Two different things had been treated as one:

- **The in-loop judge** — `usecases/verify_visual.py`, called automatically inside the designer loop,
  which runs headless in the harness with no agent attached. It genuinely needs a programmatic
  client and a key. Decision 017 governs this, correctly.
- **Grading a fixed 8-case suite** — 5 planted defects and 3 controls, inspected once, offline,
  against a rubric. No client, no credential, no CI involvement.

Decision 017 said nothing about the second, but its title ("Live Call Is Operator-Gated, Out of CI")
was read as a blanket ban — by the implementation stories, by the scorer, by two tests, and by me.

### What it unblocked, in order

1. **The judge was measured**: 5/5 detected, 0/3 controls flagged. Sensitivity 1.000, false alarm
   0.000, Wilson CI [0.566, 1.000] at n=5.
2. That exposed **the scorer's hard-coded assumption** — it forced `not_scored` on `visual_judge`
   whenever it held no credential, overwriting a real measurement. Fixed so a graded results file is
   a first-class outcome source alongside the in-FreeCAD drivers.
3. That exposed **two tests encoding the same stale premise**. Both rewritten to assert the rule
   rather than today's registry state; one now injects its own unmeasured validator rather than
   depending on one existing.
4. That exposed **a genuinely stale G1 grader hash**. A `ruff format` pass had changed `grader.py`
   bytes, staling a score measured over the old ones. Re-scored: 16/16, CI [0.806, 1.000].
5. Separately, the `verify_sketch` suite landed: 13 planted + 7 controls, all driven, 1.000 / 0.000,
   CI [0.772, 1.000].

**G3 leg-b now passes: every cited validator current and at bar.**

### Two errors of mine worth recording

**I over-generalized a correct diagnosis.** Having correctly identified one flaky G3 test as my own
interference (reading files an agent was writing), I dismissed five G1 failures the same way. They
were real — they failed in isolation — and were a stale hash needing a re-score.

**My first caveat test was vacuous.** It asserted that a judge-graded row carries a confidence
caveat, keyed on a field named `judge`; the registry writes `graded_by`. The assertion never ran. I
found it only by deleting the fields and watching the test still pass. That is the third instance of
this defect class in this epic (DW-114 was the first, the TechDraw probe the second) — an assertion
that passes whether or not the thing it names exists. **The habit that catches it is cheap: delete
the thing the test asserts, and confirm the test fails.**

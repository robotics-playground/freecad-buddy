## Intent

**Problem:** Every Phase-2 capability G2 measures now exists — 18 geometry-mutation tools, the AD-5 bracket, `document_undo`, the TNP guard, the confirm gate — but **no code path drives a mutation from a gate run**. `_collect_report` (`benchmarks/runner.py:318`) has a hardcoded G0-only dispatch, so `run G2` writes six `not_collected` FAIL reports; `run_exit_command:570` hard-refuses any gate but G1 (`--exit is only defined for gate G1`); none of G2's five cited validators (`assertions`, `run_mutation`, `fingerprint`, `audit_references`, `verify_sketch`) is registered in `benchmarks/_registry/validators.yaml`, so verdict leg-b fails all five; 24 of 28 fault cases still carry `fixture: pending`; and `benchmarks/g2/heldout/` holds **8 plaintext case directories committed to git** rather than the sealed pair the `verdict.heldout: sealed` contract assumes.

**Approach:** Land the G2 exit machinery on the pattern Story 2.4 established for G1 — generalize the runner off its gate-id branches onto the declarative `gate.yaml`, add a live G2 criterion collector driving real mutation tools in-FreeCAD, materialize the four pending fault suites and score the five validators into the registry, and seal `g2/heldout/` for real (unlike G1's empty placeholder, G2's held-out cases exist). The live pass-rate stays the operator ceremony decisions 010/011 fixed; CI proves the machinery, the leg math, and the refusals offline.

## Boundaries & Constraints

**Always:**
- The verdict stays a **pure function over stored files** (AD-13). Criterion collectors write `ValidationReport`s; `derive_verdict` re-derives every verdict and the stored `verdict` field is never trusted. Re-running the verdict on identical files reproduces the identical result.
- **Generalize, never add a second gate-id branch.** `_collect_report` and `run_exit_command` currently branch on the literal `"G0.2"`/`"G1"`. G2 support is a declarative dispatch keyed off `gate.yaml` (the gate's own `verdict.heldout`, `criteria[].id`, `cited_validators`), matching how `check_exit_run` already detects sealed gates.
- **`run G2 --exit` is the only path that unseals `g2/heldout/`.** Key-gated on `FREECAD_BUDDY_UNSEAL_KEY`, `archive_sha256` verified before extraction, `unseal_events` appended, temp extraction deleted in `finally`, set burned on a failed exit. Dev runs stay held-out-blind. The burn trigger stays legs a+c only (the narrowing Story 2.4's follow-up review landed) so an unattested token cannot burn the set.
- **Fault fixtures are materialized by the tools that plant them**, through the real mutation path — a fixture hand-built to look like a defect does not validate the guard that must catch it. Each materialized case records `planted_op`, following `rollback-boundary/build_rollback_fixtures.py` (the one suite Story 3.2 already did this way).
- **A validator's score is citable only while current** (NFR2): each of the five is scored against its fault suite at sensitivity ≥95 % / false-alarm ≤5 %, written to `_registry/validators.yaml` with its `validator_sha`, and stales when the validator source changes.
- **G2.4 must not score `UNSUPPORTED` as a pass or a fail by accident.** `audit_references` returns wholesale `UNSUPPORTED` when `shim.element_map_available()` is false (`usecases/tnp_guard.py:439-444`); the collector probes element-map availability first and reports `UNSUPPORTED` as an explicit criterion failure on a matrix leg, never as clean.
- **The benchmark drives the confirm gate it is measuring.** `gate.yaml:26` declares `profile: confirmed-mutation`; the driver mints a real `preview_id` per command via `preview_dry_run` and passes it as `confirm`, so approval records read `mode: "preview_token"`. `FREECAD_BUDDY_AUTO_APPROVE` is not the benchmark path.
- Runner exit-code contract unchanged: 0 pass / 1 honest-fail / 2 usage-or-loader error; never a traceback.
- In-FreeCAD purity holds for anything the driver runs inside `FreeCADCmd`: stdlib + FreeCAD API only. The harness modules stay FreeCAD-free and deterministic under test (timestamps/`git_sha` injected).

**Block If:**
- The story is read as requiring the **live ≥85 % G2.1 pass-rate asserted green in this run**. That is an operator ceremony needing a real MCP-client actor, not an unattended-CI deliverable — the closed precedent is decisions 010/011 and Story 2.4's identical Block-If. This story ships the machinery and an honest-failing offline run; it does not fabricate the number.
- **G2.6's ablation harness** is required as Epic-3 code. `epic-3-context.md:79` assigns the ablation harness to shared infrastructure, not Epic 3, and every Epic-6 story is `backlog`; no ablation runner, no McNemar, and no marker identifying which 6 of the 15 `skills/` dirs are "newly drafted" exist. If the intent is read as "build the ablation harness here", HALT: it is a different epic's deliverable.
- Sealing `g2/heldout/` requires **rewriting git history** to expunge the already-committed plaintext cases. Sealing going forward is in scope; history rewriting on `main` is not an unattended operation.

**Never:**
- Never open, read, or quote `benchmarks/g2/heldout/` case content outside the `--exit` unseal path — including while writing or testing this story. Filenames and manifest metadata only.
- Never let the offline machinery dry-run masquerade as the operator exit: an offline `--exit` is labelled a dry-run over a scripted double, exactly as G1's prints it (`runner.py:597-600`).
- Never route an actor's own claim into a verdict, never average an oracle disagreement, never count a fault case toward any pass rate.
- Never add a third-party dependency for sealing (decision 012), and never commit the unseal key or place it in CI secrets.

## Design Notes

**Why generalize rather than branch.** `run_exit_command` refuses on `gate != "G1"` and `_collect_report` dispatches on literal G0 criterion ids. Both predate a second real gate. `check_exit_run` already shows the intended shape — it keys off `gate_def["verdict"]["heldout"] == "sealed"`, so it engages for G2 with no edit at all. The exit path needs the same treatment: a per-gate eval seam looked up from the gate, not an `if`-ladder that grows one arm per epic.

**Why the driver mints a real token instead of setting the auto-approve posture.** `gate.yaml:26` declares `profile: confirmed-mutation` and the confirm gate is Phase-2 functionality under test. `FREECAD_BUDDY_AUTO_APPROVE=1` would bypass it, and the difference is observable — approval records carry `mode: "auto_approve"` rather than `mode: "preview_token"`. The constraint this imposes: `_SECRET` is per-process (`usecases/confirm.py:32`) and the token signs the fully-defaulted params, so preview and apply must run in one process with byte-identical args.

Per case, the driver's sequence and what each criterion reads from it:

```
pre = fingerprint(doc)["digest"]                     # G2.3 expectation
pv  = dispatch("preview_dry_run", {doc, operation})  # -> preview_id
env = dispatch(tool, {**args, doc, confirm: {preview_id, elicitation_action: "accept"}})
m   = env["structured_content"]["mutation"]          # G2.2: post_verify, rolled_back, explanation
                                                     # G2.4: m.post_verify.tnp_audit.status
                                                     # G2.5: m.post_verify.fully_constrained
checks = assertions.evaluate(doc, case["assertions"]["checks"])   # G2.1
u   = dispatch("document_undo", {doc, expect_fingerprint: pre})   # G2.3: u.matches_pre_op
```

**Why the driver installs an audit sink rather than the collector reading envelopes alone.** `gate.yaml:55` names both sources — "read audit log + reports" — but `_sketch_method`/`_feature_method` construct handlers with no `audit_sink` (`tool_catalog.py:335-340`), so today the log's mutation lines carry `fingerprint_before/after: null` and `rollback: null` while the envelope's `mutation` block carries all of it. Reading envelopes only would satisfy the arithmetic and silently drop half the criterion's declared evidence. The driver therefore threads a real `AuditSink` (`FREECAD_BUDDY_AUDIT_LOG` pointed at the run dir) so both sources are populated, and G2.2 cross-checks them: the envelope is primary, and a mutation whose envelope and audit line disagree is a criterion failure rather than a resolved-by-preference reading. Records join on `params_digest`, since `transaction_id` is the constant `"0"` (`transaction.py:42`).

**Why the held-out seal is weaker for G2 than for G1.** G1 sealed an empty placeholder, so nothing was ever exposed. G2's 8 cases are in git history in plaintext. Sealing now prevents further casual reading and makes the ceremony enforceable, but it cannot restore the property that no one has seen them. The README must say so; a seal that implies more integrity than it has is worse than a documented weaker one.
